# 1.1.9 分片续传测试失败审计

本地记录时间：2026-10-02 18:47（Asia/Hong_Kong）。本次仅修改 HTTP 测试夹具；生产下载代码未修改。证据使用随机生成的 2 MiB 数据和本地 HTTP 服务，不包含用户整合包、存档、账户或网络凭据。

## 失败与原因边界

候选版本两轮全量测试均为 639/640，失败位置都是 `download-tail-1100.test.ts` 的 `starts.includes(8192)`。原始失败记录保留，不改写为通过。

旧夹具将第一次到达 `/mirror` 的 HTTP 请求重定向到慢节点，却要求续传起点固定为 8192。两个 1 MiB 分片并发启动，各自异步查询缓存文件，HTTP 到达顺序不保证从第零分片开始。若第一分片先到，慢节点保留其 8192 字节后，正确的绝对续传偏移是 **1048576 + 8192 = 1056768**，而不是 8192。

只读观察的一轮全量测试通过了 640 项。随后仅在忽略目录内的观察器中，为第零分片缓存查询增加 40 毫秒延迟，控制合法的异步完成顺序，稳定复现同一断言失败，同时确认最终文件完整。这证明旧夹具的顺序依赖；两轮原始失败未采集 HTTP 顺序，因此不声称已观测到它们各自的具体到达顺序，也没有证据证明全量测试污染了下载阈值。

## 最小修复

只把第零分片的第一次请求路由到慢节点，其余分片及续传请求路由到健康节点，不依赖哪个分片先到。不串行化产品，不增加产品延迟，也不放宽断言。

保留 `redirects >= 3`、精确的 `starts.includes(8192)` 和最终文件 SHA1 一致断言；另增加 `mirrorStarts.includes(8192)`，明确保证续传重新访问镜像入口，而非锁定第一次跳转的节点。
